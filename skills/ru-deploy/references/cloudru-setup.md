# Cloud.ru: виртуалка, домен, DNS, HTTPS

**Цель документа:** довести стадию B — у пользователя есть ВМ на Cloud.ru, агент заходит на неё по SSH, домен указывает на сервер, порты 80/443 открыты.

**Что делает агент:**
1. Объясняет пользователю про free tier и бонусы, ведёт его по созданию ВМ (логин/пароль задаёт пользователь).
2. Когда первый вход даёт `Permission denied` — даёт пользователю команду для браузерной консоли (включить парольный вход + fail2ban) и дожидается «готово».
3. Помогает выбрать домен (по умолчанию `<IP>.sslip.io`).
4. Проводит пользователя по открытию портов 80/443 в группе безопасности.
5. Проверяет: вход по SSH работает, домен резолвится, порты открыты снаружи.

Объясняй пользователю простыми словами; кнопки в панели Cloud.ru нажимает только он.

## 0. Как устроено облако Cloud.ru (объясни пользователю своими словами)

Cloud.ru — российский облачный провайдер. Нужная нам часть называется **Evolution**. Внутри Evolution мы берём **виртуальную машину (ВМ)** — это, по сути, отдельный компьютер в дата-центре, который работает круглосуточно и доступен из интернета. На нём мы и поднимаем backend проекта.

Главное, что важно понять про оплату — ресурсы тарифицируются **по отдельности**, не «пакетом»:

- **Сама ВМ** (процессор, память, диск) — есть бесплатный уровень (free tier).
- **Публичный IP-адрес** (белый адрес, по которому сайт виден из интернета) — **платный отдельно**, в free tier НЕ входит.
- **Выход в интернет** с ВМ — тоже требует публичного IP или платного SNAT-шлюза.

### Что входит в бесплатный уровень (free tier)

| Ресурс | Бесплатно |
|---|---|
| Виртуальная машина | 1 шт: 2 vCPU / 4 ГБ RAM / 30 ГБ SSD, гарантированная доля CPU 10% |
| Объектное хранилище | 15 ГБ |
| Срок акции | до 31 декабря 2026 |
| Условие | положительный баланс на аккаунте |

Этого хватает на один учебный проект (нехватку памяти на 4 ГБ страхует swap, его включает `server-setup.sh`). Доля CPU 10% — на пике сайт может подтормаживать, для учёбы нормально.

### Засада: публичный IP платный

Бесплатная ВМ сама по себе **не видна из интернета** — для этого нужен публичный IP, а он стоит **≈146 ₽/мес** (IPv4 — дефицитный ресурс, поэтому бесплатно не дают). Без него (или без платного SNAT) у ВМ нет даже исходящего интернета.

**Лазейка:** при регистрации и **привязке банковской карты** Cloud.ru даёт **4000 бонусов (= 4000 ₽), действуют 60 дней** (акция «4000 рублей для физлиц на тестирование Evolution»; бонус — за первую привязанную карту, 1 бонус = 1 ₽). Этими бонусами оплачивается публичный IP (~146 ₽/мес): 4000 ₽ хватает на IP примерно на **2 месяца с большим запасом**. То есть первые ~60 дней публичный сайт фактически бесплатный, дальше ~146 ₽/мес за адрес (бонусы нельзя тратить на ВМ с GPU, но нам GPU и не нужен).

## 0.1. Как попробовать совсем бесплатно

Три варианта — предложи пользователю по ситуации:

1. **Локально на своём компьютере (совсем бесплатно, первый шаг).** Поднять Supabase локально через Supabase CLI, фронт на `localhost`. Идеально, чтобы убедиться, что проект ожил после Lovable, не платя ничего. Минус: сайт виден только самому пользователю, не публичный.
2. **Свой компьютер + Cloudflare Tunnel.** `cloudflared` делает исходящий туннель и даёт бесплатный публичный HTTPS-адрес **без белого IP**. Можно показать другим. Минусы: компьютер должен быть включён; быстрый туннель (`trycloudflare`) даёт временный адрес, меняющийся при перезапуске (для стабильного — бесплатный аккаунт Cloudflare + свой домен).
3. **Cloud.ru free ВМ, IP за бонусы 4000 ₽ (~60 дней).** Настоящий публичный сайт на сервере: сама ВМ — free tier, публичный IP (~146 ₽/мес) оплачивается приветственными бонусами 4000 ₽ за привязку карты. Бесплатно ~2 месяца, потом ~146 ₽/мес за IP.

**Рекомендуемый путь для ученика:** сначала вариант 1 (локально, проверить), затем вариант 3 (Cloud.ru + бонусы, выложить настоящий сайт на 60 дней). К концу бонусов уже ясно, нужен ли проект и стоит ли платить за IP.

> ⚠️ Cloudflare Tunnel **не** спасает на самой Cloud.ru-ВМ для «совсем без IP»: там и исходящий интернет платный, туннелю не за что зацепиться. Туннель хорош именно для своего компьютера/домашнего сервера, у которого интернет уже есть.

## 1. Аккаунт Cloud.ru

1. Зарегистрироваться на https://cloud.ru (по телефону/почте).
2. Зайти в консоль **Evolution**.
3. Пополнить баланс на минимальную сумму — у free tier есть условие «баланс должен быть положительным».

## 2. Создать виртуальную машину

Консоль → **Evolution Compute** → создать виртуальную машину:

- **ОС:** Ubuntu 22.04 LTS (или новее).
- **Конфигурация:** минимум 2 vCPU / 4 ГБ RAM / 30 ГБ SSD. Free tier ровно такой — этого хватает для одного учебного проекта (swap включает скрипт установки).
- **Сеть:** включить публичный IP-адрес.
- **Доступ:** добавить **SSH-ключ** пользователя. Если ключа нет:
  ```bash
  ssh-keygen -t ed25519        # на компьютере пользователя, Enter на все вопросы
  cat ~/.ssh/id_ed25519.pub    # это вставить в поле SSH-ключа при создании ВМ
  ```
- Создать. Записать **публичный IP**.

## 3. Брандмауэр / Security Group

Очень важно для безопасности: наружу открыть **только** порты:

- `22` (SSH), `80` (HTTP), `443` (HTTPS).

Порт `8000` (Supabase/Kong) наружу **не открывать** — к API ходят только через Caddy по 443. Настраивается в разделе сети/безопасности ВМ в консоли Cloud.ru.

## 4. Включить вход по паролю + проверить доступ

### Почему отдельный шаг

Образ Cloud.ru по умолчанию пускает по SSH **только по ключу** (`PasswordAuthentication no`). Логин и пароль, которые пользователь задал при создании ВМ, работают в **браузерной консоли** Cloud.ru, но **не** при `ssh` снаружи — попытка даёт `Permission denied (publickey)`. Поэтому для простого пути (вход по логину/паролю, как хочет новичок) надо один раз включить парольный вход.

### Включить вход по паролю (делает пользователь, 1 раз, в браузере)

Пользователь открывает: панель **Cloud.ru → его ВМ → кнопка «Консоль»** (туда логин/пароль пускают) и вставляет **одну** команду целиком:

```bash
sudo bash -c 'sed -i "s/^#*PasswordAuthentication.*/PasswordAuthentication yes/" /etc/ssh/sshd_config; sed -i "s/^#*PasswordAuthentication.*/PasswordAuthentication yes/" /etc/ssh/sshd_config.d/* 2>/dev/null; systemctl restart ssh || systemctl restart sshd; apt-get update -y >/dev/null 2>&1; DEBIAN_FRONTEND=noninteractive apt-get install -y fail2ban >/dev/null 2>&1; printf "[sshd]\nenabled = true\nmaxretry = 20\nfindtime = 600\nbantime = 600\n" > /etc/fail2ban/jail.local; systemctl enable fail2ban; systemctl restart fail2ban; echo OK-PASSWORD-SSH-READY'
```

Команда: (1) включает парольный SSH, (2) перезапускает SSH, (3) ставит **fail2ban** с умеренным порогом — банит IP после **20 неудачных** попыток за 10 минут (`maxretry=20, findtime=600, bantime=600`). Жёсткий дефолт fail2ban (`maxretry=5`) банил саму машину агента из-за частых подключений; корневую причину решает ControlMaster (агент ходит через одно ssh-соединение, см. SKILL.md → «Хелпер для ssh-команд»), а умеренный порог — дополнительная страховка. Бот-переборщик паролей всё равно отсекается. Когда в консоли появилось `OK-PASSWORD-SSH-READY` — готово.

> **Безопасность.** Открытый парольный вход на публичном IP боты будут долбить перебором. fail2ban это закрывает. Дополнительно стоит позже сменить пароль на длинный (12+ случайных символов): агент может сгенерировать его и поменять командой `echo "$RU_USER:НОВЫЙ_ПАРОЛЬ" | sudo chpasswd`, обновив `.ru-deploy/credentials.env`. Слабые пароли вида `Слово1!` подбираются по словарю.

### Альтернатива для продвинутых: вход по ssh-ключу

Если пользователь умеет работать с ключами — добавить публичный ключ в консоли (`echo 'ssh-ed25519 AAAA...' >> ~/.ssh/authorized_keys`) и не включать парольный вход. Минус для новичка: ключ привязан к одному компьютеру, с другого не зайти. Для скилла **по умолчанию рекомендуем пароль** — он переносимый и проще объясняется.

### Проверить доступ (делает агент)

После включения — проверь вход по логину/паролю (см. SKILL.md → «Доступы к серверу»):
```bash
set -a; . .ru-deploy/credentials.env; set +a
export SSHPASS="$RU_PASS"   # пароль через env, не в argv
sshpass -e ssh -o StrictHostKeyChecking=accept-new -o UserKnownHostsFile=.ru-deploy/known_hosts "$RU_USER@$RU_HOST" "echo OK; whoami"
```
Должно вывести `OK` и логин пользователя. Системные команды на сервере запускай через `sudo` (у дефолтного пользователя Cloud.ru `sudo` обычно без пароля).

## 5. Домен

Caddy получает бесплатный HTTPS-сертификат **только если есть домен, указывающий на IP сервера**. Покупать домен необязательно — для новичка есть бесплатный путь. Предложи пользователю выбор и **по умолчанию рекомендуй вариант А** (быстрее всего, без регистрации и оплаты).

### Вариант А (рекомендуемый по умолчанию): бесплатный домен `<IP>.sslip.io`

[sslip.io](https://sslip.io) (и запасной [nip.io](https://nip.io)) — это «магический» DNS: любое имя вида `212.34.56.78.sslip.io` автоматически резолвится в IP `212.34.56.78`. **Ничего регистрировать, настраивать или платить не нужно** — IP уже зашит в имя.

- Домен пользователя = `<IP-виртуалки>.sslip.io` (например `212.34.56.78.sslip.io`). Дефисный вид `212-34-56-78.sslip.io` тоже работает.
- A-запись настраивать **не нужно** — она «встроена». DNS уже указывает на сервер, можно сразу идти на шаг 2.
- Резолвится из России, Caddy выдаёт Let's Encrypt из коробки (HTTP-01 challenge проходит, т.к. имя и есть IP).

Когда использовать: учебный/pet-проект, демо, «просто чтобы заработало». Минус — «некрасивое» имя с цифрами; для бренда позже переедете на свой `.ru` (вариант Б).

Проверка:
```bash
ping <IP>.sslip.io     # должен показать тот же IP
```

> **Важно для агента (rate limit Let's Encrypt).** Лимит сертификатов на зоны `sslip.io`/`nip.io` общий на всех пользователей мира. Поэтому: (1) Caddy хранит сертификаты на постоянном volume (`server-setup.sh` это обеспечивает — не удаляй `/data` Caddy при пересборках); (2) не гоняй пересоздание контейнера Caddy циклически; (3) если выдача упёрлась в ошибку `too many certificates already issued` — переключи домен с `sslip.io` на `nip.io` (тот же формат `<IP>.nip.io`) и перезапусти Caddy.

### Вариант Б: свой домен `.ru` (почти бесплатно, «красивое» имя)

Если нужен человекочитаемый домен (`мой-проект.ru`):

1. Зарегистрировать `.ru` у российского регистратора (Beget, REG.RU — часто ~189 ₽/год, по акциям дешевле). Оплата российскими картами.
2. Делегировать домен на бесплатный DNS регистратора (или Cloud.ru DNS) и создать запись:
   - тип **A**, имя `@` (корень), значение — **публичный IP** виртуалки;
   - по желанию ещё **A** для `www` на тот же IP.
3. Подождать обновления DNS (от пары минут до часа).

> **Предупреди пользователя:** с **1 сентября 2026** регистрация доменов `.ru`/`.рф`/`.su` требует идентификации через **Госуслуги (ЕСИА)** — для физлица это один дополнительный шаг.

Проверка:
```bash
ping <домен>          # должен показать IP виртуалки
```

**Не запускай шаг 2 (установку backend), пока `ping` не показывает правильный IP** — для варианта Б DNS должен успеть обновиться (для варианта А это мгновенно).

### Чего избегать

- **DuckDNS** (`*.duckdns.org`) — заблокирован РКН, из России недоступен. Не предлагай.
- **Cloudflare Tunnel / Serveo / ngrok-туннели** — это другая архитектура (не A-запись на сервер) и проблемы с доступностью из РФ; в наш пайплайн с Caddy не вписываются.
- Бесплатные служебные поддомены хостеров (`*.beget.tech`, `*.xsph.ru`) указывают на сервер хостера, а **не** на чужой Cloud.ru-IP — для нашей схемы не годятся (но их бесплатный DNS-хостинг можно использовать в варианте Б для своего `.ru`).

## 6. HTTPS

HTTPS поднимается автоматически: `server-setup.sh` запускает Caddy, который сам получает бесплатный сертификат Let's Encrypt для домена. Отдельных шагов не нужно.

### HTTPS не поднялся

Если `https://<домен>` ругается на сертификат или не отвечает:

1. Проверь DNS: `ping <домен>` → правильный IP.
2. **Проверь, что порты 80 и 443 открыты в брандмауэре Cloud.ru** — это самая частая причина. С локальной машины: `nc -z -G 6 <IP> 80 && nc -z -G 6 <IP> 443 && echo OK`. Если не `OK` — открой их (раздел «Брандмауэр» выше) и подожди до минуты, пока правило применится.
3. Логи Caddy: `RSH "sudo docker logs caddy --tail 50"` — там видно ошибку выдачи сертификата (`RSH` = вход логином/паролем, см. SKILL.md → «Доступы к серверу»). Признак «порты были закрыты»: `Timeout during connect (likely firewall problem)`.
4. **Если Caddy ушёл в долгую паузу или на staging-сертификат** (в логах `acme-staging` и/или `retrying_in: 600`). Так бывает, если backend подняли при ЗАКРЫТЫХ портах: Caddy несколько раз не смог выпустить сертификат, нарастил паузу между попытками и переключился на недоверенный staging Let's Encrypt. После того как порты 80/443 открыты, **не жди** — перезапусти Caddy с чистым ACME-состоянием, чтобы он сразу пошёл на прод и выпустил доверенный сертификат:
   ```bash
   set -a; . .ru-deploy/credentials.env; set +a
   RSH "sudo docker rm -f caddy; sudo docker volume rm caddy_data"
   RSH "sudo docker run -d --name caddy --restart unless-stopped --network host \
     -e DOMAIN=$RU_DOMAIN \
     -v /etc/caddy/Caddyfile:/etc/caddy/Caddyfile -v /var/www/app:/var/www/app \
     -v caddy_data:/data -v caddy_config:/config caddy:2"
   ```
   Через ~30 сек проверь: `curl -sS -o /dev/null -w "%{http_code} TLS=%{ssl_verify_result}\n" https://$RU_DOMAIN/rest/v1/` — ждём `401 TLS=0` (`TLS=0` = сертификат доверенный).
5. Лёгкий случай (порты были открыты, просто перечитать конфиг): `RSH "sudo docker exec caddy caddy reload --config /etc/caddy/Caddyfile"`.
